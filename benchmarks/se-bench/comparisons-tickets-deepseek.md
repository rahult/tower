### Build a ticket system — pi vs tower

| Dimension | pi | tower | Evidence |
| --- | --- | --- | --- |
| architecture | 7 | 8 | pi is a single-file `src/index.js` where `openTickets` returns closures over an in-memory `state` loaded once via `loadState`, with `persist()` using a pid-suffixed temp file + `renameSync`. tower centers the same file on a `mutate(path, fn)` read-modify-write seam, a stateless store whose every method re-reads via `readState`, and a declarative `{from,to}` `TRANSITIONS` table, making the JSON file the single source of truth. |
| solid | 7 | 8 | pi's `assertTitle/assertPriority/assertAssignee` and `clone()` keep units small and give strong isolation, but `update` interleaves validation with assignment, so an earlier field is mutated before a later field throws. tower's `update` validates all present fields first (`assertTitle`/`assertPriority`) before applying, and `mutate`/`requireTicket` keep read-modify-write and lookup single-purpose. |
| robustness | 7 | 7 | pi handles corrupt JSON (`corrupt ticket store`), empty files, monotonic timestamps (`lastAt`), extra `assertAssignee`, and is prototype-safe in `transition` (`TRANSITIONS[action]` then `map[status]`), but a rejected multi-field `update` leaves in-memory state partially applied. tower's `mutate` leaves the file byte-identical when `fn` throws, but `transition(id,'toString')` dereferences `TRANSITIONS['toString'].from` and throws a TypeError instead of the spec's `invalid transition` Error, and it has no corrupt/empty-file guard. |
| testing | 8 | 8 | pi's 15 tests cover defaults, id reuse on reopen, every validation message, filtering (incl. `assignee:null` and invalid status), the full transition matrix, timestamps, empty-file reopen, and defensive-clone isolation, but never a multi-field update where a later field fails. tower's suite adds the strong invariant `a rejected mutation leaves the file bytes untouched` and a raw file-shape assertion plus transition-persistence checks, but omits returned-object isolation. |
| documentation | 5 | 6 | Both `README.md` files are the same `(Implementation to be written.)` placeholder, so neither documents the API for a new user; pi adds only sparse inline comments about the `lastAt` guard and `TRANSITIONS`, while tower's `openTickets` carries an accurate JSDoc block describing sync durability, re-read-per-call semantics, and atomic replace. |

**Verdict: tower (slight)** — Both are complete, well-tested single-file libraries that pass all acceptance checks. tower is better engineered because it treats the JSON file as the single source of truth through its `mutate` read-modify-write seam, so a failed mutation never changes state, whereas pi caches state in memory and can expose a partially-applied update after validation fails.

Key difference: tower's stateless re-read-and-write keeps memory and disk consistent on any rejected mutation, while pi's cached `state` diverges from the file after a multi-field `update` throws mid-application.
