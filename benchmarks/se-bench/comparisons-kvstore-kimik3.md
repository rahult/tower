### Build kvstore — pi vs tower

| Dimension | pi | tower | Evidence |
| --- | --- | --- | --- |
| architecture | 7 | 8 | Both are a right-sized single src/index.js closure, but tower factors real seams: readAt/hasAt parameterized over a staged overlay serve both store and tx, applyOp/applyRecord serve both replay and commit, and readRecords isolates JSONL parsing with torn-tail policy. Pi has decent helpers and a nice uniform {ops:[...]} record format, but it parallel-implements the read path (tx.get vs get) and the apply path (replayLog's op loop vs applyChanges). |
| solid | 6 | 8 | Tower has exactly one place that knows op semantics (applyOp) and one read implementation shared via the staged/null parameter, with contract messages held in BAD_KEY/NOT_SERIALIZABLE constants. Pi duplicates logic per surface — store.del unconditionally logs a del record for absent keys while tx.del stages one, replayLog re-codes op application that applyChanges also codes, and the error literals are repeated inline — creating drift risk between the store and its transaction view. |
| robustness | 6 | 8 | Tower's assertSerializable recursively rejects nested undefined/function/symbol/bigint with the exact contract message, whereas pi's serializeValue silently stores {a:undefined} as {} and [undefined] as [null]; tower also fsyncs the snapshot before truncating the WAL in close() (pi can lose both on power loss between rename and flush) and only tolerates a torn tail line while pi's replayLog/readSnapshot silently skip any corrupt line. Pi claws back points: its tx exposes transaction() so the nested error message is exact on both surfaces (tower's tx lacks the method), close() actually closes the fd and guards post-close calls with 'store is closed' (tower leaks walFd forever), and it validates that fn is a function. |
| testing | 8 | 9 | Pi covers all spec essentials with precise name+message assertions: deep-copy in both directions, both nested-transaction paths (including tx.transaction), multi-cycle crash recovery, torn-line recovery, and rollback-after-crash. Tower matches that and adds invariant-level assertions that catch subtler regressions: WAL byte-length unchanged after rollback and empty transactions, idempotent replay after an interrupted close, falsy-value presence-based dels, __proto__/constructor key safety, nested non-serializable structures, and error identity (thrown === err). |
| documentation | 4 | 5 | Both READMEs are the identical, now-false stub ('Implementation to be written.') with no API reference or usage example. Tower's inline comments carry real design rationale — fsync-before-truncate ordering in close(), the O_APPEND/single-handle assumption flagged as known limitation F1, the overlay read path — while pi's comments (torn-line tolerance, one record per transaction) are accurate but thinner. |

**Verdict: tower (clear)** — Tower is better engineered: it funnels every read and mutation through single shared implementations and validates serializability recursively and orders its close() fsyncs correctly, while pi re-implements the same logic per surface and leans on JSON.stringify's incidental behavior, silently mangling nested non-serializable values. Pi is still genuinely good — 18/18 acceptance, a thorough suite, and a cleaner close/fd lifecycle — so the margin is clear rather than decisive.

Key difference: Tower has one canonical read path (readAt/hasAt with a staged overlay) and one apply path (applyOp/applyRecord) shared by the store, transactions, and recovery — plus recursive validation and fsync-ordered snapshotting — whereas pi duplicates each surface in parallel and only rejects what JSON.stringify happens to throw on.
